Aperçu

À quoi sert ce projet

C'est l'exercice technique identity-check-qa : une fausse application de vérification d'identité (KYC), et une suite de tests automatisés qui la contrôle. Les tests vérifient le parcours au niveau de l'API et dans un vrai navigateur Chrome.

Application clienteCrée une sessionPOST /api/sessions
UtilisateurEnvoie sa pièce/verify/<id>
ServeurRend sa décisionVERIFIED · REJECTED
RésultatAPI et page web/api/sessions/<id>/result/<id>
L'application n'analyse pas la pièce

La décision dépend uniquement du nom du fichier envoyé : s'il contient invalid (majuscules ou minuscules), la pièce est refusée ; sinon elle est acceptée.

Installation

Installer sur une nouvelle machine

À faire une seule fois. Sur la machine actuelle, c'est déjà fait.

  1. Vérifier les prérequis

    Python 3.11 ou plus récent, et Google Chrome.

    python3 --version
google-chrome --version

  2. Installer Poetry

    Poetry est l'outil qui gère les librairies du projet.

    pipx install poetry
# ou, sans pipx :
python3 -m pip install --user poetry

  3. Installer le projet

    Poetry crée le dossier .venv dans le projet et y installe toutes les librairies (Flask, Selenium, pytest…).

    cd identity-check-qa
poetry install

  4. Optionnel : créer le fichier de configuration

    Les valeurs par défaut fonctionnent. Ce fichier sert seulement à les changer.

    cp .env.example .env
Activer le .venv (facultatif)

Après source .venv/bin/activate, on peut taper pytest au lieu de .venv/bin/pytest. La commande deactivate en sort.

Utilisation

Lancer les tests

Inutile de démarrer le serveur avant : les tests le démarrent eux-mêmes et l'arrêtent à la fin.

.venv/bin/pytest

Lancer une partie des tests

Chaque test porte des étiquettes (marqueurs). L'option -m choisit lesquels lancer.

CommandeCe qui est lancé
.venv/bin/pytest -m smokeLes parcours principaux : pièce acceptée et pièce refusée, API et navigateur
.venv/bin/pytest -m apiTests API seulement, sans navigateur (le plus rapide)
.venv/bin/pytest -m uiTests dans Chrome
.venv/bin/pytest -m e2eParcours complets de bout en bout
.venv/bin/pytest -m negativeCas d'erreur : session inconnue, envoi sans fichier…
.venv/bin/pytest -m securityContrôles de sécurité (injection HTML)
.venv/bin/pytest -m "not known_defect"Tout sauf les défauts connus de l'application
.venv/bin/pytest -k specimenLes tests dont le nom contient « specimen » (carte d'identité spécimen)

Si un XFAIL devient FAILED

Un défaut a été corrigé dans l'application : le test passe alors qu'il était censé échouer (XPASS). Supprimer les lignes @pytest.mark.known_defect et @pytest.mark.xfail(...) au-dessus de ce test.

Le rapport de la dernière campagne est dans test_report.html, à la racine du projet.

Exploration manuelle

Utiliser l'application à la main

  1. Démarrer le serveur

    Il reste actif dans ce terminal. Ctrl+C l'arrête.

    .venv/bin/python -m mock_server.app

  2. Créer une session (dans un second terminal)

    curl -X POST http://127.0.0.1:5005/api/sessions
# {"session_id": "a1b2c3d4e5f6", "status": "PENDING"}

  3. Envoyer une pièce dans le navigateur

    Ouvrir http://127.0.0.1:5005/verify/a1b2c3d4e5f6 (avec l'identifiant reçu), choisir un fichier de tests/fixtures/, puis cliquer sur Submit capture. La page de résultat s'affiche.

  4. Ou envoyer la pièce par l'API

    curl -X POST http://127.0.0.1:5005/api/sessions/a1b2c3d4e5f6/document \
  -F "document=@tests/fixtures/specimen_cni_recto.jpg"

Arrêter le serveur avant de lancer les tests

Le serveur manuel et les tests utilisent le même port (5005). Autre possibilité : laisser le serveur tourner et lancer les tests avec IDCHECK_START_MOCK=false .venv/bin/pytest.

Configuration

Paramètres

Tous les réglages passent par des variables d'environnement, ou par le fichier .env. Une variable passée dans la commande l'emporte sur le fichier.

VariableDéfautRôle
IDCHECK_BASE_URLhttp://127.0.0.1:5005Adresse de l'application testée
IDCHECK_START_MOCKtruetrue : les tests démarrent le serveur eux-mêmes. false : ils utilisent celui qui tourne déjà à IDCHECK_BASE_URL.
IDCHECK_HEADLESStruefalse pour voir la fenêtre Chrome
IDCHECK_BROWSERchromeNavigateur utilisé (seul Chrome est pris en charge)
IDCHECK_API_TIMEOUT10Délai maximum d'un appel API, en secondes
IDCHECK_UI_WAIT_TIMEOUT10Délai maximum d'attente d'un élément de page, en secondes

Exemple : tester un autre environnement sans toucher au code.

IDCHECK_START_MOCK=false IDCHECK_BASE_URL=http://recette.exemple:5005 .venv/bin/pytest
Faire évoluer

Ajouter un cas de test

Nouvelle pièce d'identité

Déposer le fichier dans tests/fixtures/, puis le déclarer dans tests/support/documents.py :

PASSEPORT_SPECIMEN = DocumentScenario(
    id="specimen-passeport",
    file=FIXTURES_DIR / "specimen_passeport.jpg",
    expected_status=Status.VERIFIED,
)

DOCUMENT_SCENARIOS = [..., PASSEPORT_SPECIMEN]

C'est tout. La pièce est automatiquement testée par l'API et dans Chrome, soit 4 tests de plus.

Nouveau test

Ajouter une fonction test_... dans le fichier qui correspond. Les « fixtures » prêtes à l'emploi se reçoivent en paramètre :

FixtureFournit
api_clientLe client pour appeler l'API (create_session, submit_document, get_status)
pending_sessionUne session neuve, au statut PENDING
make_documentCrée un fichier temporaire avec le nom et le contenu voulus
upload_pageLa page d'envoi de pièce, pilotée dans Chrome
result_pageLa page de résultat, pilotée dans Chrome
 
def test_pdf_document_is_verified(api_client, pending_session, make_document):
    document = make_document("carte.pdf")

    result = api_client.submit_document(pending_session.session_id, document)

    assert result.status == Status.VERIFIED

Dépannage

Problèmes fréquents

« Cannot bind http://127.0.0.1:5005 »

Un serveur tourne déjà sur le port 5005, souvent un serveur lancé à la main. Soit l'arrêter avec Ctrl+C dans son terminal, soit réutiliser ce serveur :

IDCHECK_START_MOCK=false .venv/bin/pytest

Pour trouver le processus qui occupe le port :

ss -ltnp | grep 5005
« .venv/bin/pytest: No such file or directory »

Le .venv n'est pas installé, ou la commande n'est pas lancée depuis le dossier du projet. Se placer dans le dossier, puis lancer poetry install.

Les tests navigateur sont en ERROR au démarrage

Au premier lancement, le pilote de Chrome (chromedriver) est téléchargé automatiquement : il faut une connexion Internet cette fois-là. Vérifier aussi que Chrome est installé avec google-chrome --version.

Les tests API fonctionnent sans Chrome : .venv/bin/pytest -m api.

« poetry: command not found »

Installer Poetry (étape 2 de l'installation), puis ouvrir un nouveau terminal.

Un test échoue avec « Expected status 'VERIFIED', last displayed: … »

La page de résultat n'a pas affiché le statut attendu dans le délai prévu. Relancer le test seul avec IDCHECK_HEADLESS=false pour voir ce qui se passe à l'écran. Sur une machine lente, augmenter IDCHECK_UI_WAIT_TIMEOUT.

Sécurité

Règles à respecter

  • Jamais de vraie pièce d'identité dans tests/fixtures/. Utiliser des fichiers factices ou des spécimens officiels marqués « SPÉCIMEN ».
  • Jamais de mot de passe ni de clé API dans le code. Ils vont dans .env, qui n'est pas versionné, ou dans un coffre à secrets.
  • Ne pas rendre le dossier .venv avec l'exercice. Il est volumineux et propre à chaque machine ; le correcteur le recrée avec poetry install.
  • Contre un vrai service KYC : ne pas journaliser le contenu des pièces, ne pas faire de captures d'écran des pages de capture, et utiliser un environnement de test dédié.
